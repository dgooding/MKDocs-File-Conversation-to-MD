01 · Abstract

Abstract

A bounded, structure-preserving conversion apparatus for translating Office Open XML and Portable Document Format streams into self-contained Markdown while maintaining invocation-channel parity.

[0001]The disclosure provides a stateless processing system configured to accept byte sequences identified as DOCX or PDF, route each sequence to one authoritative conversion function for its format, preserve recoverable hierarchy, inline styling, links, tables, and raster imagery, and expose the resulting Markdown through direct function calls, HTTP contracts, editable preview rendering, and isolated batch packaging. The preferred embodiment uses an in-memory DOCX normalization stage followed by MarkItDown 0.1.7 and a geometry-aware PDF pipeline based on pdfplumber, pypdfium2, and Pillow. Image-only PDF pages are preserved visually and may be subjected to an optional Tesseract adapter when a two-factor scan heuristic is satisfied.

[0001A]In one embodiment, the apparatus comprises a format-routing boundary, format-specific conversion authorities, a constrained rendering boundary, and an archive-producing batch boundary. The processing system is configured to preserve a common Markdown contract while selecting different semantic recovery mechanisms for each source information model. The conversion engine maintains invocation parity by preventing delivery adapters from implementing independent transformations.

[0002]The system distinguishes technical completion from human fidelity. Exact direct/API and direct/batch equality are enforced, while fidelity assertions require source-to-output inspection. Repeated page furniture is removed by document-level normalization and counting; hyperlinks are recovered through character-to-annotation rectangle overlap; images are rendered, cropped, normalized to CSS pixel dimensions, content-hashed, deduplicated, and embedded as data URIs. Batch failures are localized to per-file terminal states and successful outputs are emitted with a manifest in an in-memory ZIP archive.

[0003]Measured The retained suite contains 36 passing tests. Measured Eight pilot PDFs comprise 45 pages, 45 unique source images, 24 unique source URIs, and eight detected table regions. Measured The current workspace occupies 384.23 MiB; 130.61 MiB is attributable to a measured MarkItDown-exclusive candidate dependency closure. Calculated Subtracting that closure from the measured 213.65 MiB environment yields an 83.04 MiB residual, not yet established by a clean build.

02 · Field

Technical Field

Document interpretation, layout recovery, semantic normalization, safe rendering, and stateless conversion-service deployment.

[0004]The subject matter lies at the intersection of document compiler design, computational document analysis, geometric layout interpretation, content-addressed asset processing, API contract engineering, and containerized service execution. It concerns transformation from layout-bearing or semantically styled source representations into a linear, human-editable Markdown representation.

[0005]The DOCX path treats Office Open XML as a semantic package that may nevertheless encode headings only through direct visual formatting. The PDF path treats a page description as positioned characters, annotations, grids, and image objects rather than as a preexisting paragraph tree. The two formats therefore share an output contract but do not share an extraction algorithm.

Purpose
Recover useful document semantics without claiming pixel equivalence.
Mechanism
Format-specific extraction followed by a common Markdown and invocation contract.
Operational constraint
Only DOCX and PDF suffixes are accepted by the implemented API.
Validation evidence
Validated Direct, API, batch, rendering, scanned-page, and deployment-policy tests.
03 · Background

Background and Problem Statement

Markdown is structurally sparse; DOCX and PDF encode meaning through incompatible combinations of semantics and visual arrangement.

[0006]A DOCX file may contain explicit Heading styles, list numbering definitions, relationships, tables, and embedded media. It may instead contain visually apparent headings represented as ordinary paragraphs with bold and enlarged runs. A direct semantic converter preserves the first class and flattens the second unless preprocessing promotes cautiously inferred headings.

[0007]A PDF generally contains no normative paragraph, heading, or table tree. Reading order must be inferred from character geometry, font metrics, grid intersections, annotations, and page-object locations. Page headers and footers recur but are not intrinsically marked as furniture. Images may repeat on every page. A visually dominant scan can contain almost no text objects.

[0008]The conversion problem is therefore not a serialization change. It is a lossy compilation problem in which the target grammar cannot represent pagination, exact typography, floating placement, merged-cell topology, or arbitrary page geometry. Correctness requires explicit invariants: preserved textual content, useful hierarchy, recoverable references, stable output across invocation channels, controlled failure, and honest separation between automated structure checks and human fidelity judgment.

Problem boundary. The implementation does not promise pixel equivalence, general optical understanding, semantic interpretation of charts, password decryption, digital-signature preservation, or universal reading-order recovery.

06 · Invariants

Architectural Invariants

These properties constrain all preferred embodiments and current extension work.

I-1: Format authority. convert_docx(bytes) -> str and convert_pdf(bytes) -> str are the sole conversion authorities. HTTP and batch layers delegate; they do not reimplement format semantics.
I-2: Interface parity. For the same input byte sequence, API and batch Markdown must equal the direct function result exactly.
I-3: Native semantics first. Native OOXML and PDF geometry precede OCR; targeted OCR precedes full-page visual fallback.
I-4: Optional-provider isolation. Missing Tesseract does not prevent DOCX or born-digital PDF conversion.
I-5: Diagnostic separation. Status, duration, error detail, and review state reside in API or manifest metadata, not published Markdown.
I-6: Evidence separation. Technical completion is not human fidelity approval.
I-7: Checkpoint execution. One approved checkpoint is implemented and validated before another begins.

[0010]These invariants reduce semantic drift by making converter functions the computational center and the surrounding API, UI, batch, and deployment layers adapters rather than competing implementations.

If native extraction throws or produces blank Markdown, the current preferred embodiment invokes a MarkItDown PDF fallback. That fallback is planned for removal but remains implemented at the evidence cutoff.

[0012]Pass one scans text lines whose top coordinate is within the top ten percent or whose bottom coordinate lies below ninety-two percent of page height. Text is lowercased, whitespace-collapsed, and digit runs replaced by #. A normalized string observed at least twice becomes repeated furniture.

[0013]Pass two computes median visible character size per page, renders the corresponding page at scale two, and calls _page_items. The item extractor excludes repeated furniture and table-overlapping lines, classifies list and heading forms, merges compatible paragraph lines, adds normalized tables, crops image objects, and emits blocks sorted by their top coordinate. From page two onward, <!-- page N --> marks source page boundaries without exposing conversion diagnostics.

11 · Algorithms

Heading Inference Algorithms

Separate algorithms are required because DOCX exposes paragraph semantics while PDF exposes positioned glyphs.

DOCX direct-format inference

if empty or style begins Heading/Title: no inference
if style begins List or numbering exists: no inference
if every visible run is not explicitly bold: no inference
S = maximum explicit run font size in points
if S >= 17: Heading 1
else if S >= 15: Heading 2
else if length(text) <= 60 and final character not in : . ; ! ?: Heading 3
else: no inference

[0014]Promotion changes only the temporary document. Each run in a promoted paragraph has bold, size, and color reset to inherited style values, preventing direct formatting from being emitted twice by the downstream semantic converter.

PDF geometric inference

[0015]Let B be the median visible character size on a page. An extra-large line whose size is at least max(18, 1.55B) becomes level one only on the first page when no heading item has been emitted; otherwise it becomes level two. A left-aligned line no longer than ninety characters and lacking terminal .;!? becomes level two when size is at least 1.15B, or level three when bold and size is at least 0.95B.

Rationale
Median page size is robust to a small number of title outliers; punctuation and alignment reduce false-positive prose headings.
Tradeoff
Page-relative statistics may flatten document-wide hierarchy; font-name bold detection depends on embedded font naming.
Limitation
No learned classifier, style-history model, or multi-line heading merger exists.
Evidence
Validated Semantic and visually inferred DOCX headings; H1/H2 PDF fixture headings and exclusions for labels/list items.
12 · Tables

Table Reconstruction Logic

DOCX tables are semantic; PDF tables are geometric regions normalized into a rectangular Markdown grammar.

[0016]DOCX table conversion is delegated to the current semantic engine after heading preprocessing. PDF table extraction calls page.find_tables(), records bounding boxes, excludes ordinary line extraction within those boxes, and passes extracted rows to _table_markdown.

  1. Determine maximum row width and pad shorter rows.
  2. Collapse internal whitespace and escape literal pipe characters.
  3. Remove columns empty across all rows.
  4. If at least four columns remain and every row has no more than two populated cells, split at the midpoint and collapse each half into a two-column representation.
  5. If one column remains, produce a blockquote callout.
  6. Flush multi-cell row segments as Markdown tables; represent intervening one-cell rows as bold section labels.
  7. For a one-row multi-column region, synthesize an empty header and retain the row as data.
Purpose
Preserve cell content and readable grouping under Markdown's rectangular table constraint.
Rationale
Sparse PDF grids frequently encode field/value layouts or callouts rather than conventional tabular headers.
Tradeoff
Cell spans, border weights, column widths, and precise visual topology are flattened.
Validation
Validated Standard two-column output, sparse six-column normalization, single-column callout conversion, one-row fallback, and pipe escaping by implementation.
13 · Links

Hyperlink Recovery Mechanisms

DOCX relationships are semantic; PDF links are spatial annotations requiring geometric assignment to characters.

[0017]For each PDF character, the converter constructs an axis-aligned rectangle from x0, x1, top, and bottom. It compares the rectangle with each page hyperlink annotation containing a URI. Any non-disjoint pair associates the character with the annotation URI.

[0018]Consecutive characters sharing bold, italic, and URI state are grouped. Formatting is applied to the group and then wrapped as [text](uri). URIs are percent-encoded while preserving standard scheme, path, query, fragment, and email punctuation. A mailto annotation whose visible text is angle-bracketed is normalized to avoid redundant brackets.

MechanismStrengthFailure mode
DOCX relationship extractionExplicit source relationship and anchor textUnsupported or malformed relationship may be dropped by the underlying converter
PDF rectangle overlapRecovers annotation targets independent of visible URL textOversized or misregistered rectangles can associate neighboring characters
Preview renderingmarkdown-it-py rejects unsafe link schemesProduced Markdown remains editable data and is not itself a security boundary

14 · Images

Image Preservation Architecture

Images are embedded in the Markdown itself to avoid a second asset publication protocol.

DOCX image path

MarkItDown is invoked with keep_data_uris=True. The retained test decodes a known embedded PNG and requires the complete base64 payload; a prior truncating form ending in base64... is explicitly rejected.

PDF image path

  1. Render the page to RGB at scale two.
  2. Map PDF-space image bounds to raster coordinates using independent horizontal and vertical scale factors.
  3. Reject zero-area crops.
  4. Crop the rendered page and resize to round(width * 96/72) by round(height * 96/72) using Lanczos resampling.
  5. Encode optimized PNG bytes.
  6. Compute SHA-256 and suppress a byte-identical image already emitted anywhere in the document.
  7. Base64-encode and emit ![Image from page N](data:image/png;base64,...).
Rationale
Self-contained Markdown survives download, ZIP packaging, and isolated preview without asset-path coordination.
Tradeoff
Base64 increases representation size and browser decode work; deduplication intentionally removes repeated logos.
Limitation
PDF images are raster crops of rendered pages, not necessarily original encoded streams; generic alt text does not describe content.
Evidence
Validated Complete DOCX image bytes, one output for two identical PDF images, expected 53×53 CSS-pixel result, and scan-page visual preservation.
15 · OCR

OCR Detection and Routing

OCR is a conditional adapter, not a mandatory converter dependency.

Figure 5. OCR decision tree

Visible native characters < 40 AND maximum page-covering image ratio > 0.55?
NoUse native text, geometry, tables, links, and images. Do not call OCR.
YesAlways preserve the visual image. Detect optional OCR adapter.
Provider availableRender RGB page → Tesseract stdin/stdout → normalize OCR text → include with visual content.
Provider absent or failsReturn visual content without searchable OCR text; unrelated conversion remains available.

The classifier requires both sparse native text and dominant image coverage; neither factor alone routes the page to OCR.

[0020]TesseractOCR.detect checks TESSERACT_CMD, the process PATH, and three standard Windows installation locations. Candidate executables must return zero from --version within four seconds. Extraction serializes RGB input as PNG and invokes tesseract stdin stdout -l eng --psm 6 with a sixty-second timeout. Nonzero exit, timeout, operating-system error, or empty output returns no text.

Evidence boundary. Validated Routing and graceful absence are tested with a fake provider and a missing executable. Assumed Real Tesseract OCR quality is not validated because Tesseract is absent on the workstation.
16 · Rendering

Markdown Rendering System

Preview generation is distinct from conversion and is constrained to a safe CommonMark profile.

[0021]The renderer initializes MarkdownIt("commonmark") with raw HTML, automatic linkification, and typographic substitutions disabled, then enables table syntax. render_markdown is a pure string-to-string boundary. The API exposes this through POST /api/render with a Pydantic request model containing one Markdown string.

Purpose
Provide a browser-review representation without allowing converted or edited Markdown to inject raw HTML.
Rationale
Conversion and rendering have different trust boundaries; generated Markdown remains editable and must be re-rendered under explicit policy.
Tradeoff
Legitimate source HTML is displayed as text; linkification and typographic transformation are intentionally absent.
Limitations
The renderer is not a general HTML sanitizer for arbitrary plugin output; safety depends on the configured parser profile.
Evidence
Validated Headings, tables, embedded raster data images, blocked script tags, blocked JavaScript links, and blocked SVG data images.

18 · Batch

Batch Conversion Architecture

A synchronous per-file state machine localizes failures and packages successful outputs with deterministic collision handling.

State machine behavior

UnsupportedSuffix absent from converter registry
EmptyContent byte sequence is falsey
ErrorAuthoritative converter raises
SuccessMarkdown, duration, size, unique output name

Each file reaches exactly one terminal state. Unsupported, empty, and error states do not terminate processing of subsequent files.

[0024]The module-level converter registry maps .docx and .pdf to the same functions used by the single endpoint. Successful filenames are formed from the source stem. A case-folded set detects collisions and appends -2, -3, and subsequent suffixes.

[0025]For each success, elapsed time is measured with time.perf_counter and rounded to one decimal millisecond; UTF-8 Markdown byte length is recorded. The manifest includes a twelve-hex-character batch identifier, UTC timestamp, aggregate status counts, and serialized per-file records. The archive is a DEFLATE-compressed BytesIO containing successful Markdown entries followed by manifest.json.

Tradeoff
Simple deterministic isolation without queue infrastructure; entire batch remains synchronous and memory-resident.
Recovery behavior
Client retries the request after process/request failure; no resume token exists.
Validation
Validated Mixed DOCX/PDF outputs, exact direct parity, duplicate output naming, manifest equality, separate batch page, ZIP API, and 25-file rejection.

20 · Container

Containerization Strategy

A multi-stage locked build separates dependency resolution from the rootless runtime.

  1. Copy uv 0.12.5 from its dedicated image.
  2. Use python:3.12-slim-bookworm as builder.
  3. Copy only project metadata, lockfile, and source.
  4. Execute uv sync --frozen --no-dev --no-editable.
  5. Use a fresh Python slim runtime and install libgomp1, currently required by the retained ONNX chain.
  6. Copy the builder virtual environment.
  7. Set group ownership/permissions compatible with arbitrary OpenShift UIDs.
  8. Redirect HOME and XDG cache to /tmp, disable bytecode writes, and enable unbuffered output.
  9. Run as UID 1001 and expose an HTTP health check.
Purpose
Exclude build tools, test dependencies, and host-environment contamination from runtime.
Rationale
Frozen lock resolution and a clean builder provide reproducibility superior to copying the Windows `.venv`.
Tradeoff
The virtual environment is still copied wholesale; image size tracks runtime dependency closure.
Limitation
Base-image digest is not pinned; no SBOM, signature, or vulnerability evidence exists.
Validation
Validated Static policy assertions for frozen sync, rootless user, health command, port, permissions, and build-context exclusions. Runtime execution remains unvalidated.

22 · Reliability

Reliability Model

Reliability is obtained through deterministic computation, failure isolation, and restartability rather than durable workflow state.

[0027]Conversion functions are stateless with respect to prior requests. Repeating a conversion with identical bytes and dependency versions is expected to reproduce the same Markdown, and tests enforce equality across channels. The service can therefore recover from process replacement by retrying the entire request.

Implemented controls

  • Empty and unsupported input rejection.
  • Per-file batch exception isolation.
  • Optional OCR failure isolation.
  • Health endpoint and orchestration probes.
  • Frozen dependency graph.
  • Verified external backup.

Absent controls

  • Durable queues and idempotency keys.
  • Partial-batch resume.
  • Timeouts around primary conversion.
  • Circuit breakers and admission control.
  • Multiple replicas or disruption budget.
  • Structured telemetry and SLOs.
Failure domain
A converter exception affects one single request or one batch item; process failure affects all in-flight work.
Recovery
Retry from source bytes; Kubernetes may restart a failed container; no intermediate recovery state exists.
Operational constraint
One worker and one declared replica; concurrency characteristics are not validated.

Error Handling Framework

Errors are translated at ownership boundaries and deliberately excluded from published Markdown.

Unsupported suffixNo converter selectedHTTP 415 / batch unsupportedSupply DOCX or PDF

Batch count/size violationReject requestHTTP 400/413; no partial archiveSplit or reduce batch

Failure scenarios

  1. A malformed PDF causes the native route to throw; current code suppresses the exception and attempts MarkItDown. If both fail, API returns 422.
  2. A page meets scan criteria but Tesseract times out; no OCR text is appended, while extracted visual blocks remain.
  3. A large image-heavy batch exceeds process/container memory before the API's byte limit reflects expanded raster/base64 output; the process may terminate and no ZIP is returned.
  4. A batch contains one malformed file; that item becomes error and subsequent files continue.

30 · Recovery

Recovery and Rollback Strategy

Recovery operates at request, deployment, source, dependency, and archive layers.

Request recovery

Because the service is stateless, failed work is retried from original bytes. Individual batch failures can be retried separately using manifest status.

Deployment recovery

Readiness removes an unhealthy endpoint; liveness is intended to trigger restart. OpenShift Deployment revision rollback is available as a platform behavior but has not been exercised locally.

Source and environment rollback

A verified Safe Lean backup exists at C:\MKDocsbackup\Docs-to-MK-safe-lean-20260817-203034. Dependency-minimization work is checkpointed so source, manifest, and lock can be restored before recreating the environment. Individual packages are never to be deleted manually from site-packages.

Toolchain coupling. The active .venv\pyvenv.cfg points to the project-local Python under .tools\python312. Deleting only .tools breaks the environment. Externalization requires rebuilding the virtual environment against a verified external interpreter first.
31 · Governance

Governance and Development Rules

Development controls are part of the disclosed engineering system because they protect behavioral invariants.

  1. Complete exactly one approved checkpoint at a time.
  2. Before editing, state purpose, expected files, and focused validation.
  3. After validation, report and stop for approval.
  4. Keep one authoritative conversion function per format.
  5. Add exact interface parity tests for Markdown and later approved assets/metadata.
  6. Keep diagnostics out of published Markdown.
  7. Treat optional converters and OCR providers as adapters.
  8. Prefer native semantics, targeted OCR, then visual fallback.
  9. Separate technical success from fidelity.
  10. Use structural assertions rather than volatile whole-file snapshots.
  11. Never call automated ratings human review.
  12. Restore archived evaluation artifacts only for an explicitly approved fidelity review.

[0033]These controls narrow blast radius and ensure a failed hypothesis is detected before a second behavior slice changes. The rules are operational constraints on preferred implementation evolution, not end-user requirements.

33 · Constraints

Known Constraints

Constraints prevent overstatement of the apparatus.

  • Supported source suffixes are DOCX and PDF only.
  • Exact Word/PDF visual layout is not representable in the target Markdown grammar.
  • Encrypted/password-protected PDFs may fail.
  • Multi-column reading order is not generally solved.
  • Complex merged-cell tables are normalized rather than preserved geometrically.
  • Image alt text is generic and not machine-captioned.
  • Real Tesseract quality is unmeasured; absence yields visual-only scan preservation.
  • DOCX Office equation behavior is not covered by retained tests and is a planned probe before dependency replacement.
  • Batch is synchronous, limited to 25 files and 100 MiB source bytes, and not resumable.
  • No single-file limit, durable queue, timeout around primary conversion, or concurrency semaphore exists.
  • No authentication, authorization, rate limiting, malware scanning, audit logging, retention policy enforcement, or tenant isolation exists.
  • Container and OpenShift definitions have not been executed locally.
  • OpenShift declares one replica and no disruption budget or autoscaler.
  • No Windows packaged executable is implemented.
  • No Git release, CI/CD pipeline, SBOM, signature, or production rollback exercise is evidenced.

37 · Conclusion

Conclusions

The disclosed system is a bounded document compiler with explicit semantic, operational, and evidentiary contracts.

[0035]The apparatus does not treat DOCX and PDF as interchangeable containers. It assigns each format an extraction strategy appropriate to its information model while constraining both to one Markdown result boundary. DOCX semantic structure is augmented only where conservative visual evidence exists. PDF structure is reconstructed from character geometry, page statistics, annotations, grids, rasterized image regions, and optional OCR.

[0036]The principal systems property is not any individual parsing heuristic but the composition of format authority, invocation parity, conditional fallback, per-file isolation, self-contained asset output, safe rendering, and evidence-controlled validation. This composition makes behavior inspectable and regression-resistant while preserving explicit limits.

[0037]Validated The active system supports controlled internal DOCX/PDF conversion, editable preview, individual download, mixed batch ZIP output, and image-only-page visual preservation under 36 retained tests. Unvalidated Production security, real OCR quality, actual container/OpenShift operation, high availability, scale, and formal human fidelity remain outside the current evidence boundary.
